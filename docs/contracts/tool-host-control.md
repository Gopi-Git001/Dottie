## 1. Scope and roles

- **Coordinator (K3, E03)** owns the single active task and its turns (ADR-0010; CONTRACTS §5 ruling "the single active task"). It is the only source of `taskId`/`turnId` for tool calls. **[RULED]** CONTRACTS §5 "Tool-host context".
- **Tool host (K9, E04/E11)** is the `dottie-tools` server, hosted per ADR-0008 (MCP stdio child of App Server, option B; or dynamic tools, option A, decided by W1-S2/DOT-005). It treats every model-chosen argument as untrusted (ARCHITECTURE §6 TB7).
- **K8 (policy gate + audit, E08)** mints and checks the tool-server token (ADR-0009 CR6) and holds `k8Key` (CONTRACTS §3.3). K8 is a main-process module (ARCHITECTURE §3 K8, §4).
- **Secure UI (K2, E06)** is the only channel that approves a category that needs confirmation, i.e. anything except `read` and `navigate` (ADR-0009 CR3 and item 8 incl. the `navigate` exception, CONTRACTS §3 `ApprovalRequested`, DOT-087).
- **Out of scope:** the tool schemas (`docs/contracts/tools.md`, E04, CONTRACTS §5), the App Server wire (CONTRACTS §1), the shared events themselves (CONTRACTS §3), the renderer IPC (`docs/contracts/desktop-ipc.DRAFT.md`).

## 2. Transport and framing (§(a))

### 2.1 What the docs fix
- K3 and K8 live in Electron main (ARCHITECTURE §4; ADR-0005). **[RULED]**
- Under ADR-0008 option (B) the tool host is a **child of App Server**, i.e. a grandchild of Electron (ARCHITECTURE §4 process tree; ADR-0008 "Evidence added"). Its stdio belongs to Codex (MCP). The coordinator therefore **cannot** use the host's stdio, and Codex makes the MCP call, so the coordinator cannot add data to the MCP request. **[RULED]** (consequence of ADR-0008 + ADR-0009 CR6 "the tool server gets it over a K8 channel; Codex can't see or forge it").
- Under option (A) the host is an E04 worker spawned by Electron main (ADR-0008 "Evidence added"), so a direct stdio pipe exists.
- IPC messages are schema-validated on receipt and rejected on an unknown `version` or type; no secrets cross IPC except where a contract says so; correlation ids are logged, payloads only after redaction (CONTRACTS §4). **[RULED]**
- No listening socket for Codex (TB4: "local pipe only"). WebSocket transports are not used (ARCHITECTURE §4). **[RULED]** for App Server; applied here by analogy **[PROPOSAL P1]**.

### 2.2 Transport (**[PROPOSAL P1]** shape + **[PROPOSAL E-P1]** naming, E04 + **[E08 1]** DACL and peer checks; depends on ADR-0008)
| Host option (ADR-0008) | Channel | Who creates it | Peer check |
|---|---|---|---|
| (B) MCP stdio, grandchild | Windows **named pipe** `\\.\pipe\dottie-toolhost-<h>` (E-P1 naming below); DACL and flags per **[E08 1]** below | Electron main, **before** spawning App Server | **Both ways**, per **[E08 1]** below |
| (A) worker spawned by main | the worker's **stdin/stdout** (stderr → redacted diagnostic log), like App Server (CONTRACTS §1) | Electron main | implicit (main owns the process) |

**Pipe name — derived, not delivered [PROPOSAL E-P1, E04; accepted by E08 1].** `h` = first 32 hex chars of SHA-256(`"dottie.toolhost.pipe.v1"` ‖ user SID ‖ logon session id). Both ends compute it from their own process token, so nothing has to cross the CONTRACTS §1.1 env allowlist or the persisted `config.toml`. The hash keeps the SID out of the object namespace. The name is **not a secret** and nothing relies on it being one. **No handshake secret** (E08 1: a random name or secret has no clean carrier — the env needs a Codex pass-through (UNVERIFIED), `config.toml` and argv are persisted, and Codex controls the final spawn, so handle inheritance can't be relied on).

**Squatting [PROPOSAL E-P1, E04; E08 1, 9].** If main's first-instance create fails because the name exists (`ERROR_ACCESS_DENIED` / `ERROR_PIPE_BUSY`), someone squatted it: **do not start the tool host**, set a `RuntimeStatus` warning (CONTRACTS §2.4), write audit `toolhost.pipe_squatted` (outcome `refused_start`, reason `name_exists`; §5.7), and **never** fall back to another name silently.

**DACL, flags and peer checks [E08 1] (E08 wording):**
> DACL: one ACE granting `GENERIC_READ|GENERIC_WRITE` to the **logon SID** of Electron main's token (no Everyone, Authenticated Users, `NETWORK`, Users, or bare user-SID grant); owner = the user; mandatory label Medium (no-write-up). `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, `nMaxInstances = 1`.
> Server-side peer check (main), all must pass:
> 1. `GetNamedPipeClientProcessId` → PID, plus `GetProcessTimes` start time.
> 2. The client is a member of the Job object Electron main created for the `codex app-server` child (`IsProcessInJob(client, dottieJob)`; the job is created before the spawn, and descendants inherit it). This replaces the parent-chain walk, which may remain as an extra check.
> 3. The image path is the installed tool-host executable, and its SHA-256 (or Authenticode signer once signing exists) matches the value pinned at build time (same rule as the app-server binary, TB4).
> 4. The client token's user SID and logon SID equal main's.
> Client-side check (host): `GetNamedPipeServerProcessId` → the server image is the Dottie main executable with a matching start time, and the host opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`, so a squatting server can't impersonate it.
> A refused peer is disconnected and audited (`toolhost.peer_rejected`). A refused peer never counts as "the one live connection".

- Audit reasons for a refused peer (§5.7): `not_in_job | image_mismatch | start_time_mismatch | sid_mismatch | second_connection`, and **[E08 R4]** `catalog_mismatch` (a host whose `hello.catalog` differs from the pinned catalog, §4.0). Only K8 in main writes them (X1). The `toolhost.*` records **omit** `actionId`, `taskId` and `toolId` (§5.7, E08 R4); per **[E01 amendment, item 24]** these fields are optional in CONTRACTS §3.2 only for `toolhost.*` and required for every other kind (validator enforces per kind).
- Exactly **one** host connection at a time. A second connection is refused while the first is live (`second_connection`). **[PROPOSAL P1]**
- **UNVERIFIED, must be checked on Gopi's PC before H-13/K-08 can pass (E08 1; W1-S2/DOT-005):** whether Codex runs the MCP child under a **restricted or AppContainer token** or a **Low integrity level**. If it does, the logon-SID ACE and the Medium label must be re-checked, because such a token may fail the ACE or the no-write-up label.
- Scope calibration (E08): personal single-user PC. These controls stop accidental or opportunistic cross-talk, squatting and impersonation by *other* processes; they do not claim to stop malware running as Gopi.

### 2.3 Framing (**[PROPOSAL P2]**, consistent with CONTRACTS §1)
- **Newline-delimited UTF-8 JSON**, one message per line, same as the App Server wire (CONTRACTS §1; ARCHITECTURE §4). A line > **64 KiB** is a protocol error (connection closed).
- Message kinds mirror JSON-RPC without the `jsonrpc` member (CONTRACTS §1): **request** `{id, method, params}`, **response** `{id, result}` or `{id, error}`, **notification** `{method, params}` (no `id`).
- Every request and notification carries a `params.v` header (§7). Unknown `method` → error `{code:'INVALID_ARGUMENT'}` for requests, logged and dropped for notifications. Unknown keys anywhere → rejected (strict schemas, as in desktop-ipc §1 step 3 and tools.md §1 `additionalProperties:false`).
- Response envelope follows `desktop-ipc.DRAFT.md` §1: `result` = `{ok:true, data}` or `{ok:false, error: ToolError}`, where `ToolError = {code, message, retryable}` from CONTRACTS §5. `message` never echoes model arguments or token values. Transport-level failures (bad JSON, oversize line, unknown version) use the JSON-RPC `error` member with `-32600` and close the connection.
- `id` is a string, unique per sender for the life of the connection (`c:<n>` from coordinator, `h:<n>` from host).
- **Host I/O [PROPOSAL E-P2, E04]:** one reader thread; requests matched by `id`; the MCP stdio loop never blocks on the pipe for longer than the call's own deadline.

**[E08 R2] What K8 records after an accepted consume (E08 wording, verbatim; replaces DRAFT 4's "If K8's reply arrives late, … `consumed_not_dispatched`"):**
> Once K8 accepts a consume (answers `consumed:true`), the approval is `executed` and can never mint or re-mint again, whatever happens next: a host timeout, a late reply, a crash, a disconnect or a lying report. At acceptance K8 writes `tool_token.consumed` with `outcome:'postcondition_unknown'`. It writes a second `tool_token.consumed` record for the same `actionId` only on an explicit `toolCallFinished` for that `callId`:
> - `phase` ∈ {`not_started`, `before_send`} with `sideEffect:'none'` → `outcome:'consumed_not_dispatched'`;
> - `phase` ∈ {`after_send`, `completed`} → `outcome:'consumed'`.
>
> No report before IPC disconnect, `endTask` or main shutdown → the outcome stays `postcondition_unknown` (on disconnect K8 adds `reason:'ipc_disconnect'`), and the call counts as `possible` in the ledger (P21, §2.4). It is never recorded as not dispatched. An outcome never moves down after `consumed`: P21 never-downgrade applies to these records too. The host's report changes only the audit and ledger wording, never K8's authority state.

- **Scope of R2 **[E08 ruling 2 2026-10-19]** (E08 wording):** R2's 'can never mint or re-mint again' applies to approval tokens (purpose `dottie.approvalToken.v1`) only. Recovery tokens (`dottie.recoveryToken.v1`) are governed by ADR-0017 and are minted only from an executed approval before its expiry, which is exactly item 35.

### 2.4 Connection loss
- **[RULED]** ADR-0009 CR1: an IPC disconnect resolves every pending approval as **decline** (Codex: `decline`/`cancel`) and dismisses the dialog; audit `decision:'cancelled'`, `reason:'ipc_disconnect'` (CONTRACTS §3.2).
- **[RULED]** ADR-0009 item 7 + CONTRACTS §3.3: any K8 token not yet consumed is **revoked**.
- **[PROPOSAL P3]** (E04 agrees, E-P2) Host side: while disconnected the host has no context, so every new `tools/call` returns `PRECONDITION_FAILED` (`sideEffect:'none'`, not retryable) and nothing runs (same code as "no active turn", §4.3); in-flight calls stop at their next cancellation point (§6.5) and report honestly. Coordinator side: any call that had passed `authorizeToolCall` and was not reported finished is recorded in the ledger as `possible` side effect if the tool is mutating (§6.4), and the task is not reported as cleanly stopped.

## 4. Message catalog (§(b))

Direction: **C→H** coordinator to host, **H→C** host to coordinator. All `params` start with `v` (§7). Timestamps are ISO-8601 with offset (CONTRACTS §3).

### 4.0 `hello` (H→C request, first message) **[PROPOSAL P7]**
```ts
type HelloParams = {
  v: 1;
  protocol: 'dottie.toolhost';
  versions: number[];                 // supported control versions, e.g. [1]
  hostVersion: string;                // build id of dottie-tools
  catalog: Array<{                    // the host's tool list, so ToolStart.mayHaveSideEffects is not guessed
    toolId: string;                   // area.verb_object (CONTRACTS §5)
    category: ApprovalCategory;       // REQUIRED; must EQUAL the pinned catalog entry (X2); CONTRACTS §3 enum

    // no `mutating` field: needs-confirm/mutating is DERIVED from the pinned category (E-P6, X2)
  }>;
};
type HelloResult = { ok: true; data: { version: 1; active: ToolCallContext | null } } | { ok: false; error: ToolError };
```

- **[CODE]** `ports.ts` `ToolStart.mayHaveSideEffects`: "Adapter/tool catalog (E04) declares whether the call can change external state. **Unknown ⇒ true**".
- **Authoritative catalog [E08 X2] (E08 wording):** "The authoritative catalog (`toolId → category, scope`) is pinned in `packages/contracts` and reviewed by E08. `hello.catalog` must equal it exactly. Any difference refuses the host (`PRECONDITION_FAILED` for every call, plus an audit record). A tool missing from the pinned catalog is needs-confirm and mutating." Categories therefore **never** come from what the host declares; `hello.catalog` is only a consistency check. This replaces E-P6's host-declared category (E04 scratch `e04_contract/catalog.py` becomes a copy-check of the pinned file). Kept from E-P6: "needs confirm" is derived (`category ∉ {read, navigate}`), never declared separately, and the pinned catalog **feeds** the adapter's "unknown ⇒ true" default. **[E08 R4]** The mismatch audit record is `toolhost.peer_rejected` (outcome `denied`) with reason `catalog_mismatch`. ### 4.1 `setActiveTurn` (C→H notification)
```ts
interface ToolCallContext {           // [CODE] ports.ts today: {taskId, turnId}
  readonly taskId: string;
  readonly turnId: string;            // `<taskId>.t<n>`
  readonly threadId: string | null;   // [PROPOSAL P4] null until threadAssigned
}
type SetActiveTurnParams = { v: 1; seq: number; context: ToolCallContext | null };
```
- **[CODE]** `beginTurn` pushes `setActiveTurn({taskId, turnId})` before each `run()`; `endTurn` pushes `setActiveTurn(null)` after the turn and when a stop is requested (`toolCallContext()` returns null once `cancelRequested`).
- **[RULED]** One active task (ADR-0010; CONTRACTS §5). At most one non-null context exists at any time.
- `seq` (**[PROPOSAL P8]**) is a coordinator-wide monotonically increasing integer; the host ignores any `setActiveTurn` with a `seq` ≤ the last one applied.
- **Token revocation [E08 6]:** on `setActiveTurn(null)` (turn end, interrupt, stop) K8 revokes every minted, unconsumed approval token of the task, and the host clears any cached `authorizeToolCall` answer on every `setActiveTurn` (X3). A later turn obtains a token only through the Option 1 re-mint (§5.3). D12.
- **Advisory only.** The host may cache it (e.g. to fail fast), but the per-call authority is `authorizeToolCall` (§4.3). A stale cache can never authorize a call. **[PROPOSAL P8]**
- `threadId` (**[PROPOSAL P4]**): `beginTurn` runs before `run()`, so for the first turn the coordinator does not know `threadId` yet. The coordinator re-sends `setActiveTurn` (new `seq`, same `turnId`) after `threadAssigned`. `authorizeToolCall` always returns the current `threadId` (CR2 needs it in `actionId`).

### 4.2 `endTask` (C→H notification)
```ts
type EndTaskParams = { v: 1; seq: number; taskId: string };
```
- **[CODE]** `closeTaskForTools`: `endTurn` (→ `setActiveTurn(null)`) **then** `endTask(taskId)`, sent after `TaskFinished` or `TaskCancelled`, only if the task was dispatched.
- On receipt the host drops all per-task state: issued `targetId`s, candidate lists, any token it still holds (it must not hold one; §5.6). K8 revokes every unconsumed token of the task (E08 6). **[RULED]** CONTRACTS §5: a `targetId` is "an opaque id issued earlier in the same task"; unknown, cross-task or ended → `NOT_FOUND`.
- **targetId lifetime (settled E03 + E04 2026-10-19, §10 C3):** a `targetId` stays valid across all turns of the same task until `endTask(taskId)` (clarification continues the same `taskId`, CONTRACTS §5 "E04 review" ruling 2). After `endTask`, or from another task → `NOT_FOUND` (CONTRACTS §5). The host's former 300 s TTL (tools.md draft §2.3) is dropped. Two host-side restrictions remain inside that window:
  - **Superseded** (E04, kept): when the **same window** is re-registered under a new id in the same task, the old id → `NOT_FOUND`. A different window's id is unaffected. **Per-window, confirmed by E04 2026-10-19 (Q-E04-8 closed):** only the re-registered window's old id is superseded; ids of other windows, and of earlier candidate lists, stay valid (E04 test TID-01e). E04 is correcting the memo §10.1 wording ("a newer candidate list supersedes").
  - **Defense-in-depth cap [PROPOSAL P23]** (E04 position, number proposed): a `targetId` older than **30 min** → `NOT_FOUND`, even if `endTask` has not arrived (guards against a lost `endTask`). It must **never** fire during a normal AMBIGUOUS round-trip: 30 min is far above the coordinator's clarification bounds (`clarificationTimeoutMs` 30 s × `maxClarificationTurns` 3, **[CODE]** README "Clarification") plus approval time (≤ 120 s per call, ADR-0009 item 7). ### 4.4 Approval round-trip: `requestApproval` (H→C request) → secure UI → `ApprovalResolved` (response)
Flow (**[RULED]** sequence from ADR-0009 CR2/CR3/CR5/CR6 and tools.md draft §5; the message shapes are **[PROPOSAL P11]**):
```
host: resolve target → compute actionId (§5.1)
host ──requestApproval{callId, actionId, binding, preview}──▶ coordinator
coordinator: validate (task/turn live, toolId in catalog, binding matches context) → K8 recompute actionId → PolicyPort
coordinator ──dottie.event ApprovalRequested{taskId, actionId, summary, risk, expiry, category}──▶ secure UI    (CONTRACTS §3)
secure UI ──dottie.event ApprovalResolved{actionId, approved, timestamp} (envelope taskId)──▶ coordinator         (CONTRACTS §3)
coordinator: resolveApproval checks (below) → if approved: K8 mints token (§5)
coordinator ──response ApprovalResolution{decision, reason, token?, expiresAt}──▶ host
```
```ts
type RequestApprovalParams = {
  v: 1;
  callId: string;
  actionId: string;                             // lowercase hex SHA-256 (CR2)
  binding: {                                    // the canonical CR2 object minus purpose; K8 recomputes actionId from it
    method: string;                             // = toolId
    args: Record<string, string | null>;        // RESOLVED absolute args (CR2), all values strings (CONTRACTS §3.3 canonicaliser)
    targets: { window: WindowIdentity | null }; // 4-field identity, decimal strings (CONTRACTS §3.3); null = launch path
    taskId: string; threadId: string | null; turnId: string; itemId: string | null; requestId: string | null;
  };
  preview: {
    summary: string;                            // ADVISORY host text; shown only under the untrusted label (E08 X5); the dialog is built from `binding`
    risk: 'low' | 'medium' | 'high' | 'critical';
    category: ApprovalCategory;                 // CONTRACTS §3 enum; 'credential_access' never reaches here (below)
    untrusted?: string;                         // [PROPOSAL] text the host read from screen/files, shown labelled untrusted (ADR-0009 item 9)
  };
};
type ApprovalResolution = {
  ok: true;
  data: {
    actionId: string;
    decision: 'approved' | 'declined' | 'cancelled' | 'denied_by_policy' | 'expired' | 'revoked';   // CONTRACTS §3.2 enum
    reason?: string;                            // CONTRACTS §3.2 reason values (user_declined, timeout, task_cancel, ipc_disconnect, …)
    token?: string;                             // present ONLY when decision === 'approved' (§5)
    expiresAt?: string;                         // token expiry (§5.4), only with token
  };
} | { ok: false; error: ToolError };            // malformed request: INVALID_ARGUMENT; no live turn: PRECONDITION_FAILED
```
Coordinator rules:
- **taskId match.** `binding.taskId`/`turnId` must equal the coordinator's live context, and `binding.threadId` its current `threadId`; otherwise `decision:'denied_by_policy'`, `reason:'task_mismatch'`, no dialog. **[RULED]** CONTRACTS §3 `ApprovalResolved` (envelope `taskId` required); **[CODE]** `resolveApproval` rejects an `ApprovalResolved` whose envelope `taskId` ≠ the pending one. Applying it to the host request is **[PROPOSAL P11]**.
- **actionId recompute.** K8 recomputes `actionId` from `binding` with `purpose:"dottie.actionId.v1"`; a mismatch → `denied_by_policy`, `reason:'wrong_action'`. **[RULED]** CONTRACTS §3.3 one canonicaliser + purpose; using `binding` for the recompute is **[PROPOSAL P11]**, accepted by E08 (item 2: K8 compares against the binding **K8 itself stored**). K8 stores this recomputed `actionId` in its approval record; it is the only value any later token or re-mint is compared with.
- **Dialog from the binding [E08 X5] (E08 wording):** "The secure UI renders the action from `binding` (method, resolved args, target) using templates in main. `preview.summary` is advisory and shown only under the untrusted label together with `preview.untrusted`. K8 rejects a `requestApproval` whose `category` or `risk` differs from the pinned catalog (X2)." **[E08 R4]** Rejection → `decision:'denied_by_policy'`, `reason:'catalog_mismatch'`; the ToolError stays `DENIED_BY_POLICY`. (Not `wrong_action`: that already means "recomputed `actionId` ≠ binding" (CR5 row), and reusing it would hide which check fired.)
- **Category floor.** `credential_access` → `denied_by_policy` (`reason:'credential_access'`), no dialog (ADR-0009 item 8). `read` inside granted scope and `navigate` (under its binding conditions) need no approval, so the host does not call `requestApproval` for them (ADR-0009 item 8 + `navigate` exception; §4.0). Locked session → deny, no dialog (ADR-0009 item 12). **[RULED]**
- **Stop requested / no live turn.** Stop requested → immediate `decision:'revoked'`, `reason:'task_cancel'`; no live turn (between turns, turn already ended) → `decision:'cancelled'`, `reason:'turn_ended'`. No dialog either way. **[RULED]** ADR-0009 CR1, CONTRACTS §3.2 table rows "turn ended or interrupted" and "panic-stop, mute, Quit, task cancel …"; **[CODE]** `approvalFromCodex` returns `{approved:false, reason:'cancelled'}` for both today (see the code gap below).
- **Time limit.** `expiry` = now + `approvalTimeoutMs` (**60 s** default, **120 s** hard max). On expiry → `decision:'expired'`, `reason:'timeout'`, and the coordinator emits `ApprovalResolved{approved:false, decision:'expired'}` to the desktop, **one per dialog (per `actionId`), before `TaskFinished`**; each joined request still gets its own audit record with `joinedTo` **[E01 ruling 1o, E08 co-signed]** (**[E01 ruling 1m]**/**[E01 ruling 1n]**, CONTRACTS @ e41d1ca §3 L215-L216; BACKLOG DOT-060 AC 10). **[RULED]** ADR-0009 item 7; **[CODE]** `awaitApproval` / `settleApproval(…,'expired', announce=true)`, config `approvalTimeoutMs: 60_000`.
- **What approves.** Only a live, in-time `ApprovalResolved{approved:true}` from `secure_ui` for that `actionId`. Tray/voice yes, unknown/reused/expired id, a yes before the request → deny. **[RULED]** ADR-0009 CR3/CR5, DOT-087; **[CODE]** `resolveApproval` (`unknown_action`, `already_resolved`, `expired`, `channel_not_allowed`).
- **Deny on cancel / revoke.** Task cancel, panic-stop, mute, Quit, lock, app-server restart and IPC disconnect resolve every pending approval as not approved. **[RULED]** ADR-0009 CR1 + item 7; **[CODE]** `runCancel` → `cancelApprovalsFor(task,'cancelled')`. **Decision values (E03 position (a), DRAFT 3): CONTRACTS §3.2 wins.** §3.2 defines task cancel as `decision:'revoked'` with `reason:'task_cancel'` (row "panic-stop, mute, Quit, task cancel, lock, app-server restart → revoked"), and keeps `decision:'cancelled'` for turn ended/interrupted, `serverRequest/resolved` and CR1 bridge failures (`ipc_disconnect`, `render_failed`, …; **`app_server_restart` comes off this list per P25** **[E08 ruling 3 2026-10-19]**: it is `revoked`/`app_server_restart` → `APPROVAL_REQUIRED` only; removed from the CR1 row in CONTRACTS §3.2 (CONTRACTS @ e089be9), with a P25 row and a "P25 tool-result mapping" paragraph added there). ### 4.5 `consumeToolToken` (H→C request), immediately before the side effect **[PROPOSAL P14]**
```ts
type ConsumeToolTokenParams = {
  v: 1; callId: string; token: string;
  actionId: string;                  // RECOMPUTED by the host at dispatch time from what it is about to do (CR6; tools.md draft §5 step 3)
  taskId: string; toolId: string;     // binding fields (§5.3); turnId is NOT part of the binding (§10 C5)
};
type ConsumeToolTokenResult =
  | { ok: true; data: { consumed: true } }
  | { ok: false; error: { code: 'DENIED_BY_POLICY' | 'CANCELLED'; message: string; retryable: false } };
```
- Order inside the host: re-read window identity (any change → `PRECONDITION_FAILED`, token not spent; CONTRACTS §5 three-step rule step 2) → recompute `actionId` → `consumeToolToken` → only on the exact success reply below, send the Win32/COM call. **[RULED]** tools.md draft §5 step 3, ADR-0009 CR6 ("consumed before the side effect"); accepted by **[E08 2]** as satisfying CR6 "the tool server verifies it", provided K8 compares with its own stored binding.
- **K8 acceptance conditions [E08 2] (E08 wording):**
  > K8 accepts the consume only if all of these hold:
  > - the `actionId` the host recomputed equals the `actionId` in K8's own token record (which K8 recomputed from `binding` at approval time, §4.4);
  > - `taskId` and `toolId` match;
  > - the token is unexpired and unrevoked;
  > - **at consume time** the task is live, no stop has been requested, the session is unlocked, Dottie is not muted, and there was no panic-stop.
  >
  > Compare-and-burn is atomic: the record is marked used synchronously, before any `await`, also on mismatch.
  > The host dispatches **only** on an exact `{ok:true, data:{consumed:true}}` response to its own request `id`. Any other shape, an unknown key, an error, a closed channel or a late reply means deny (`DENIED_BY_POLICY`, `sideEffect:'none'`).
  > No `actionId`, token or approval id is ever taken from MCP args, `_meta` or Codex.
- Burn on any attempt, including a mismatch (E04 `FakeK8.consume`; accepted by **[E08 6]**). The first successful consume moves the approval to `executed` (§5.2, E08 5/X4).
- Failure → `DENIED_BY_POLICY` (missing, unknown, malformed, reused, expired, revoked, foreign actionId/task/tool, or a consume-time state failure). **[RULED]** CONTRACTS §5 `DENIED_BY_POLICY` definition; ADR-0009 CR6. Exception: if the token was revoked **because the task was cancelled**, K8 answers `CANCELLED` with `sideEffect:'none'` so the tool result is truthful (§10 C7; **[E08 11]** accepted: audit decision stays `revoked` with reason `task_cancel` / `panic_stop` / `quit`; the tool must not execute).
- **[E08 11] (E08 wording):** "`CANCELLED` from K8 is final for that call: the host doesn't retry and doesn't request a new approval."
- Verdict mapping (E04 host positions memo §10.4; E01 ruling: `APPROVAL_REQUIRED` = grantable but not yet approved, `DENIED_BY_POLICY` = never grantable or bad authorization). `APPROVAL_REQUIRED` only ever comes from the approval stage (§4.4) or a failed re-mint (§4.5b), never from a token check:
  | consume verdict (§5.7 reason) | tool code | `sideEffect` |
  |---|---|---|
  | exact `{ok:true, data:{consumed:true}}` for this request `id` | dispatch (phase flips to `after_send`, §6.5) | — |
  | `missing`, `unknown_token`, `malformed`, `reused`, `expired`, `revoked` (non-cancel cause other than `app_server_restart`), `task_mismatch`, `tool_mismatch`, `wrong_action`, `locked`, `mute`, `gate_state_unavailable` (**[E08 R3]**: gate state unreadable, stale on the main monotonic clock, or no K8 wired; read anew, no cached allow) | `DENIED_BY_POLICY` | `none` |
  | revoked **because of a task cancel** (`task_cancel`, `panic_stop`, `quit`) | `CANCELLED` (C7, E08 11), final | `none` |
  | late call with a token revoked by **`app_server_restart`** (ruling 4 **[E01 ruling 2026-10-19 bbde9c4]**) | `APPROVAL_REQUIRED` (user may re-approve); audit `tool_token.rejected{reason:'revoked'}`, **no** second `tool_token.revoked` | `none` |
  | no K8 wired / consume timeout (2 s) / any other reply shape / closed channel / late reply | `DENIED_BY_POLICY` (fail closed, E08 2, 10) | `none` |
- **Revoked verdict vs cause **[E04 D5 fix 7]** (E04 wording):** "`revoked` is the verdict and the ToolError is `DENIED_BY_POLICY`; the audit `reason` is the cause (`superseded`, `turn_end`, `end_task`, `mute`, `locked`, `app_server_restart`, `ipc_disconnect`)". The cause is the `tool_token.revoked` reason (§5.7); a revocation by a task cancel (`task_cancel`, `panic_stop`, `quit`, `stop`) is the `CANCELLED` row instead. Exception **[E01 ruling 2026-10-19 bbde9c4]** (ruling 4): a late call with a token revoked by `app_server_restart` gives `APPROVAL_REQUIRED`, not `DENIED_BY_POLICY` (row above). **Precedence **[E01 ruling 1e, E08 confirmed 2026-10-19]** (c):** the P25 rule is the more specific signed rule and overrides this §4.5 mapping **for `app_server_restart` only**; every other non-cancel revocation (`superseded`, `turn_end`, `end_task`, `mute`, `locked`, `ipc_disconnect`, `main_restart`) keeps `DENIED_BY_POLICY` (CONTRACTS @ e41d1ca §3.2 L354).
- **Audit [E08 X1] (E08 wording):** "K8 writes the audit record for every verdict it gives. The host writes no audit. Its diagnostics go to the redacted diagnostic log and contain no args, tokens or paths." (Replaces DRAFT 3's "the host writes `policy.denied`".)
- Why a round-trip and not local verification: `k8Key` "never leaves the main process" (CONTRACTS §3.3), so the host cannot check an HMAC itself. The host's independent re-check is the **recomputed `actionId`**, which K8 compares against the binding it stored. **Accepted by E08 (item 2)** — Q-E08-2 closed.

## 5. K8 tool-server token: delivery and format (§(c)) — **E08 review**

**What K8 is.** K8 is ARCHITECTURE §3 component **K8 "Policy / permission gate & action audit"**: a main-process module owned by **E08**, "enforced again inside K9" (the tool server), providing default-deny scopes, single-use approvals and the audit log. The "K8 token" is the **single-use token issued by K8 and bound to the `actionId`** that ADR-0009 **CR6** requires on every mutating tool call, which the tool server re-checks and otherwise answers `DENIED_BY_POLICY` (TB7). It is distinct from, but modelled on, the ADR-0017 **`RecoveryToken`** (CONTRACTS §3.3), which K8 also mints with the same `k8Key`.

### 5.1 Binding inputs
- `actionId` = lowercase-hex SHA-256 of canonical JSON `{purpose:"dottie.actionId.v1", method, args (resolved absolute), targets (incl. window identity), taskId, threadId, turnId, itemId, requestId}`; fields that do not apply are `null`, never omitted. **[RULED]** ADR-0009 CR2, CONTRACTS §3 `ApprovalRequested`, §3.3.
- Window identity `{hwnd, pid, windowClass, processStartTime}`; `hwnd`, `pid`, `processStartTime` are unsigned decimal strings, no leading zeros, `"0"` invalid; `windowClass` plain string. **[RULED]** CONTRACTS §3.3, §5 (E01 2026-10-19).
- One canonicaliser (sorted keys, UTF-8, no whitespace, all values strings, duplicate/missing/non-string rejected), one test-vector suite in `packages/policy`. **[RULED]** CONTRACTS §3.3.

### 5.2 Issuance
- Minted **only** after a live, in-time `secure_ui` `ApprovalResolved{approved:true}` for that `actionId` (CR3, CR5), or by an Option 1 re-mint (§5.3, §4.5b) from that same live, unexecuted approval. Voice/tray/silence/timeout mint nothing (CR3; `FakeK8.approve` in E04 scratch). **[RULED]** + **[E08 5]**
- **Minter [E08 3] (E08 wording):** "Minted only by the K8 module in Electron main (E08-owned), which is the only holder of `k8Key`. The coordinator relays the opaque token and never logs, stores, or forwards it to the renderer." (No broker; Q-E08-3 closed.) The coordinator side needs a K8 port, e.g. `PolicyPort.mintApprovalToken(binding, approvalExpiresAt)` / `remintApprovalToken(callId, actionId)` / `consumeApprovalToken(...)` **[PROPOSAL P16]** (D7, §6.6).
- At most **one live token per approval** (E08 6). **[E08 R4]** A successful re-mint revokes any earlier unconsumed token of the same approval, so "one live token" can't deadlock (§4.5b). That revocation is audited with reason **`superseded`** **[E08 ruling 2026-10-19]** (§5.7).
- **[E08 R2]** Once K8 accepts a consume, the approval is `executed` and can never mint or re-mint again, whatever happens next (§2.3.1).
  - **Scope of R2 **[E08 ruling 2 2026-10-19]** (E08 wording):** R2's 'can never mint or re-mint again' applies to approval tokens (purpose `dottie.approvalToken.v1`) only. Recovery tokens (`dottie.recoveryToken.v1`) are governed by ADR-0017 and are minted only from an executed approval before its expiry, which is exactly item 35.
- **Approval states [E08 X4] (E08 wording):** `pending → approved → executed` (on the first successful consume), or `expired` / `revoked`.
  - An approval token can be minted only in `approved`.
  - An ADR-0017 recovery token can be minted only from an `executed` approval, before expiry, and only for restore, focus or move-to-monitor. **[E01 amendment, item 35, 2026-10-19]:** E08 X4's "(or `approved`)" is struck, because recovery restores after an action that actually ran; an `approved`-but-unexecuted approval never parents a recovery token. E01 applies the same executed-only wording to ADR-0017. ADR-0017 Decision 7 audit now uses the CONTRACTS §3.2 `recovery_token.minted` (`minted`|`refused`) / `recovery_token.used` (`executed`|`postcondition_failed`|`postcondition_unknown`) / `recovery_token.rejected` (`denied`) kinds with §3.2 decisions (`approved`, or `denied_by_policy`/`expired`/`revoked`), not `security.audit` `allowed|denied` (E01 ruling 8, 82a171b; folded per E01).
  - `consumeToolToken` must reject a recovery token, and the recovery gate must reject an approval token, both by purpose and by prefix (`k8r1.` vs `k8t1.`) (test K-05).
  - `navigate` calls never create an approval, so they never parent a recovery token beyond their own window (ADR-0009 item 8 condition 5).
  - Mapping to the CONTRACTS §3.2 `approval.*` decisions is unchanged (`approved | declined | cancelled | denied_by_policy | expired | revoked`); `executed` is a K8-internal record state, not a new audit decision (**[PROPOSAL]** E03 reading; Q-E01-13).

### 5.3 Format **[PROPOSAL P17]** (mirrors CONTRACTS §3.3 `RecoveryToken`); binding **accepted by [E08 4]**
```ts
interface ApprovalToken {               // CR6 token; held by K8 in main-process memory; never persisted
  tokenId: string;                      // 128-bit random, base64url; lookup key only, never logged (§5.7)
  actionId: string;
  taskId: string;
  toolId: string;
  nonce: string;                        // 128-bit random, base64url
  expiresAt: string;                    // ISO-8601 with offset
  mac: string;                          // HMAC-SHA-256(k8Key, canonical MAC input below), base64url
}
```
- **MAC input:** canonical JSON (CONTRACTS §3.3 canonicaliser) of `{"actionId","expiresAt","nonce","purpose":"dottie.approvalToken.v1","taskId","toolId"}`. The `purpose` value is **`dottie.approvalToken.v1`**, per BACKLOG DOT-092 "E08 follow-up 4 (2026-10-19)", confirmed by E08 4. No `turnId` in the **token** record or MAC input (§10 C5; E04 `FakeK8.mint/consume`, TOK-03/03b/03c, TOK-05/05b, TOK-09/09b/09c).
- **Wire form to the host:** opaque string `k8t1.<tokenId>.<mac>` (base64url, no padding). The host treats it as opaque and only echoes it in `consumeToolToken`. K8 looks the record up by `tokenId` and verifies `mac` in constant time. **[E08 4]** accepted.
- **Binding = `taskId + toolId + actionId`** **[E08 4] ACCEPTED.** E08's reason: "`turnId` stays in the `actionId` preimage (CR2), so the token is still bound to the turn through `actionId`. Repeating `toolId` gives K8 a cheap early reject."
- **Cross-turn calls (Q-E08-7, closed by [E08 5]):** `turnId` (and `threadId`, `itemId`, `requestId`) **stay** in the CR2 `actionId` preimage. A call re-issued in a later turn of the same task gets a token only through Option 1:
  - **Option 1 (chosen) [E08 5] (E08 wording; originally E-P3, E04):**
    > When the coordinator's K8 approval record for this `taskId` + `toolId` is live (within its 60 s/120 s limit), **not yet executed**, and the task has no stop requested, `authorizeToolCall` may return `approval: {actionId, binding:{threadId, turnId, itemId, requestId}}`. The response carries the approved ids **only, with no token**.
    > - The host recomputes `actionId` from those ids plus its freshly resolved args and window identity, then calls a new `requestToolToken{callId, actionId}`.
    > - K8 mints a fresh token only if that `actionId` equals the live approval's `actionId`.
    > - If more than one live approval exists for the same `taskId` + `toolId`, `authorizeToolCall` returns no `approval` (fail closed to a fresh approval).
    > - The approval becomes **executed** on the first successful consume and can never mint again. ADR-0017 recovery reuse keys off that executed approval until its expiry.
    > - Each re-mint writes `tool_token.minted` with `reason:'remint'`.
    > - The ids come only from K8's record, never from the host cache, `setActiveTurn`, or the MCP request.
  - **Option 2 (amend CR2): REJECTED by E08 5.** E08's reason: dropping `turnId` (and `itemId`/`requestId`) from CR2 widens cross-turn replay and weakens per-call uniqueness, and the draft names no hard technical reason that Option 1 can't solve. No CR2 / CONTRACTS §3 / §3.3 change is requested.
  - Difference from E-P3 as E04 wrote it: E-P3 put the `token` inside `approval`; E08 5 removes it and adds `requestToolToken` (E04 to update `FakeK8` / TOK-09).

### 5.4 TTL **[PROPOSAL P18]**
- `expiresAt = min(approval.expiresAt, mintTime + 10 s)`. CR6 requires "expires no later than the approval" (**[RULED]**); the 10 s cap is the proposal (the host consumes within milliseconds of receiving it; 10 s absorbs a slow identity re-check). PROVISIONAL, like ADR-0013 numbers.
- A token never extends the approval (CONTRACTS §3.3 rule for recovery tokens, applied by analogy).

### 5.5 Single use, replay and revocation
- Consumed **before** the side effect; second use → `DENIED_BY_POLICY` (audit `reason:'reused'`). **[RULED]** CR6, A9-I2.
- Foreign `actionId`, other task, other tool, expired → `DENIED_BY_POLICY`. **[RULED]** A9-I2 (missing, foreign-actionId, other-task, expired, used); the tool check is **[PROPOSAL P17]**, accepted by E08 4.
- **Revocation [E08 6] (E08 wording; replaces DRAFT 3's "not revoked at the end of a turn"):**
  > A minted, unconsumed token is revoked by:
  > - `setActiveTurn(null)`, i.e. turn end or interrupt, and every stop request;
  > - `endTask(taskId)`;
  > - task cancel, panic-stop, mute, Quit, a locked session and app-server restart (ADR-0009 item 7);
  > - IPC disconnect (CR1);
  > - main-process restart (`k8Key` regenerated).
  >
  > Cross-turn continuity exists **only** through an Option 1 re-mint from the live, unexecuted approval.
  > `expiresAt = min(approval.expiresAt, mintTime + 10 s)`. A token never extends the approval. Burned on any consume attempt, including a mismatch. At most one live token per approval.
- **Revocation audit reasons [E08 ruling 2026-10-19]:** turn end or interrupt (`setActiveTurn(null)`) → `turn_end`; normal task end (`endTask`) → `end_task`; Option 1 re-mint of the same approval → `superseded` (§5.2). Task cancel, panic-stop and stop keep their existing reasons (`task_cancel`, `panic_stop`, …) and the `CANCELLED` ToolError. Full definitions in §5.7.
- **Revocation path → `tool_token.revoked` reason **[E08 ruling 2 2026-10-19]**** (one record per unused token, §5.7):

The reason to revoke a minted token at turn end is that Option 1 now provides the legitimate cross-turn path, so a surviving token adds exposure and buys nothing.
- `k8Key` is a per-launch random key; every main-process restart invalidates all tokens. **[RULED]** CONTRACTS §3.3; §5.8.

### 5.6 Delivery and storage
- **Never** in model-visible tool arguments or results, never in MCP `_meta` (Codex builds the MCP request, so Codex would see and could forge or replay it), never in `structuredContent`, never in an event payload. Delivered only in `ApprovalResolution.token` or the `requestToolToken` reply over the control channel (§2). **[RULED]** CR6; the `_meta` exclusion confirmed by E08 2/8.
- K8: in memory only. Host: in memory only, for the lifetime of one call.
- **[E08 8] (E08 wording, appended):**
  > - The token never crosses the renderer IPC (CONTRACTS §4) and is never in model-visible args, results, `_meta`, `structuredContent` or events.
  > - K8 keeps `k8Key` and the MACs as `Buffer`s and `fill(0)` them after use where the runtime allows. This is best effort: JS strings can't be wiped, so the token string is dropped immediately after consume.
  > - The host drops its reference right after `consumeToolToken`, on `cancelToolCall`, and on `endTask`.
  > - Main and host crash dumps exclude the heap (minidump without full memory) and pass through the redactor (DOT-091 item 5).

The validator is **`validateAuditRecord`** in `packages/policy` (the `dottie.audit` schema), not `validateEvent` (ruling 2b). **One exception **[E01 ruling 1e, E08 confirmed 2026-10-19]** (b):** `policy.denied` with `reason:'schema_invalid'` carries `taskId` and `toolId` with `actionId: null`; `validateAuditRecord` allows a null `actionId` only with that reason. E08 precision: that record carries **only** `taskId`, `toolId`, `reason` and timestamps: no args (raw or partial) and no field names from the invalid payload (redactor canary test K-14) (CONTRACTS @ e41d1ca §3.2 L315). **Second exception **[E01 ruling 1h]** (CONTRACTS @ e41d1ca §3.2 L316):** `input.field_stripped` sets `taskId` when known and MUST **omit** `actionId` and `toolId` (it is not about a gated tool call). `toolId?: string` is added to §3.2 `AuditRecord` (E01 approved item 37; Q-E01-13).

### 5.8 Key **[E08 7] (E08 wording; replaces P20)**
> `k8Key` is 256 bits from the OS CSPRNG (`crypto.randomBytes(32)`). It is generated once per main-process launch, held only in K8's module scope, never persisted, logged, sent over any IPC or included in crash dumps, and regenerated on every restart, which invalidates all approval and recovery tokens. One key serves both token types, separated by `purpose` (`dottie.approvalToken.v1` / `dottie.recoveryToken.v1`). No in-process rotation in V1.

## 6. Ordering, idempotency, error codes, cancellation (§(d))

### 6.1 Ordering
- Per connection, messages are processed in arrival order (FIFO). **[PROPOSAL P8]**
- Coordinator emits per task: `setActiveTurn(t1)` → [tool calls] → `setActiveTurn(null)` → (`setActiveTurn(t2)` …) → `setActiveTurn(null)` → `endTask`. **[CODE]** `beginTurn`/`endTurn`/`closeTaskForTools`. `endTask` is sent **after** `TaskFinished`/`TaskCancelled` is emitted. **[CODE]**
- A host request that races `setActiveTurn(null)` is answered from the coordinator's current state, so it gets `PRECONDITION_FAILED`. **[CODE]** (per-call authority)
- `ApprovalResolution` for an `actionId` is sent at most once. **[CODE]** `settleApproval` deletes the pending entry and records `resolvedApprovals`.

A repeat after that is re-evaluated (normally `PRECONDITION_FAILED`)." ### 6.4 Cancellation interplay and truthful side-effect reporting
- "Stop the task" → coordinator sets `cancelRequested` → `setActiveTurn(null)` (no new call is authorized) → `cancelApprovalsFor` (pending approvals → `revoked`/`task_cancel` per CONTRACTS §3.2; the code passes `'cancelled'` today, D3; `ApprovalResolved{approved:false}` emitted) → `CodexPort.cancel(taskId)` **and** `cancelToolCall{taskId, callId:'*'}` (P15) → wait up to `cancelAckTimeoutMs`, merging `cancelToolCall` reports and `toolCallFinished` notifications (E-P5) → `TaskCancelled{stopStatus}` from observed state → `endTask`. **[CODE]** `runCancel`, `decideStopStatus`; the `cancelToolCall`/`toolCallFinished` steps are **[PROPOSAL P15, E-P5]**.
- `stopStatus` is decided from observation, never assumed. A timeout gives `stop_unconfirmed`. **[RULED]** ADR-0010, spec §14, CONTRACTS §3 `TaskCancelled`; **[CODE]** `decideStopStatus`.
- **[PROPOSAL P21]** Ledger merge: the coordinator merges `cancelToolCall` reports into the side-effect ledger and **never downgrades**: `after_send`/`committed`/`unknown` from the host wins over a `none` inferred elsewhere; a mutating call that passed `authorizeToolCall` with no report counts as `possible`. `stopped_no_side_effects` is only reported when every authorized mutating call is `phase ∈ {not_started, before_send}`. Today the ledger is fed only by `CodexRunHooks.toolStarted/toolResult` (`mayHaveSideEffects`, unknown ⇒ true), which stays.
- A token minted but not yet consumed is revoked by task cancel (ADR-0009 item 7). Revoking after the side effect ran is reported as **executed** (`already_executed`), never undone. **[RULED]** ADR-0009 item 7, CONTRACTS §3.2.
- Late tool activity after the task closed is surfaced (`coordinator.side_effect_after_cancel`, `TaskProgress` warning), never hidden. **[RULED]** spec §14, ADR-0010 Consequences; **[CODE]** `lateActivity`.
- "Stop speaking" does not cancel the task and sends nothing on this channel. **[RULED]** spec §4, ARCHITECTURE §8.

### 6.5 Phase rule and cancellation points per tool family (**[PROPOSAL E-P4, E04]**; answers Q-E04-3)
**Rule:** the host flips `phase` to `after_send` **immediately before** the side-effecting call, after the token is consumed. A cancel that races the call is therefore reported `unknown`, never `none`. `committed` is reported only when verification passed. `retryable:true` only with `none` (**[RULED]** CONTRACTS §5).
| Point | Result | `sideEffect` | phase |
|---|---|---|---|
| any refusal before dispatch (authorize, schema, scope, lookup, approval outcomes, token failures) | per §6.3 | `none` | `not_started` / `before_send` |
| cancel before dispatch | `CANCELLED` | `none` | `before_send` |
| window gone after lookup, before send | `PRECONDITION_FAILED` | `none` | `before_send` |
| sent; cancel during verify | `CANCELLED` | `unknown` | `after_send` |
| sent; window gone / unobservable | `POSTCONDITION_UNKNOWN` | `unknown` | `after_send` |
| sent; deadline without the postcondition | `POSTCONDITION_FAILED` | `unknown` | `after_send` |
| verified | `verified:true` | `committed` (or `none` if already there) | `completed` |

Cancellation points (E04, memo §10.5; Windows behaviour **UNVERIFIED** on the box):
- **COM navigate** (`IShellWindows` → `IWebBrowser2::Navigate2`): a synchronous cross-process call into `explorer.exe`; **cannot be cancelled mid-call**. Points are before (`none`) and after it returns (`unknown`). Runs on a dedicated STA worker with a call timeout; `CoCancelCall` may unblock our thread but Explorer may still navigate → `unknown`. Never retried automatically.
- **UIA waits / verify loop:** sample every **~200 ms**, check the cancel token at every sample; each UIA call bounded (~1–2 s, `IUIAutomation2` timeouts). After send, cancel → `CANCELLED`/`unknown`.
- **Playwright** (browser, DOT-034): explicit per-action timeouts; cancel = **close the page/context**; an action already dispatched → `unknown`.
- **Shell** (only if ADR-0016 selects the E04 runner, DOT-033): child in a **Job object** with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; cancel = `TerminateJobObject` (**tree kill**), then drain. Before `CreateProcess` → `none`; after → `unknown` unless the command class is read-only.
- **Files:** `MoveFileEx`/`DeleteFile` are single calls (before → `none`, after → verify). `CopyFileEx` is cancelled from its progress callback (`PROGRESS_CANCEL`); a partial copy is cleaned up and stays `unknown` unless the cleanup is verified.

## 7. Versioning (§(e)) **[PROPOSAL P22]**
- Every `params` carries `v` (the control-protocol version, starting at **1**). This is separate from the `dottie.event` envelope (`version:2`, ADR-0012) and from `dottie.audit` v1: control messages are RPC, not events.
- `hello` negotiates the highest common version; none → close. An unknown `v`, method or key is rejected, never coerced (CONTRACTS §4; the `validateEvent` rule in the coordinator-contract-change workflow).
- Additive optional fields keep `v`; any removed/renamed field, changed meaning, or new required field bumps `v`. Following `desktop-ipc.DRAFT.md` §1, both versions are supported for one release after a bump.
- Token format carries its own version (`k8t1.` prefix, MAC `purpose:"dottie.approvalToken.v1"`). A token version change is independent of `v`.
- Changes need E01 approval (spec §7) and, for §5, E08 review; a change to `ToolCallContext` follows the coordinator contract-change workflow (README table + CONTRACTS §2.5/§5 update).
