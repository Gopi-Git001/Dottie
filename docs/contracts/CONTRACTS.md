## 1. Codex App Server wire contract (Dottie ⇄ `codex app-server --listen stdio://`)

### 1.5 `CodexErrorInfo` → `CodexErrorKind` (all 21 schema alternatives: 20 named variants plus 1 open catch-all; V-schema `CodexErrorInfo`)

**Where errors come from (E01 2026-10-19, E09 pre-auth run `/workspace/dottie-e09/wire-probe/runs/preauth-linux-20261019T0112/`):** JSON-RPC error responses are always `-32600` with **no `data`** member (including not-initialized, already-initialized and unknown methods), so they never carry `codexErrorInfo`; the adapter maps them to `fatal` (protocol or programming error). `codexErrorInfo` arrives only on `error` notifications (`willRetry`) and on `turn/completed{status:'failed', error}`. A 401 shows up only as `turn/completed{failed, httpConnectionFailed{401}}` after about 14 s of `willRetry` notifications. **Retry rule, restated:** `rate_limited` or `transient` is retried only when the failed turn's ledger is empty (no side-effecting item started) and attempt < maxAttempts; a rejected `turn/start` is not a wire signal in 0.163.0.

Rules:
- An `error` notification with `willRetry:true` means Codex itself is retrying. It only produces `TaskProgress{state:RECOVERING}`; the kind is applied at the final `willRetry:false` / `turn/completed`.
- **`plan_limit` and `auth` are never retried, with no API-key fallback** (spec §5).
- `rate_limited` and `transient` follow the coordinator's bounded retry: ledger empty and attempt < maxAttempts (`retry.ts`, ADR-0012 §11).

## 2. Internal interfaces (main process only; renderer never sees them)

### 2.1 `CodexPort`: coordinator ↔ Codex adapter (owner E02 implements, E03 consumes). **Canonical = E03's port shape** (`packages/coordinator/src/ports.ts:93-98`), with v2 vocabulary

```ts
type AuthState = 'unknown' | 'unavailable' | 'signed_out' | 'signing_in' | 'signed_in' | 'expired' | 'unsupported';
type CodexErrorKind = 'transient' | 'rate_limited' | 'plan_limit' | 'auth' | 'fatal';
interface CodexPort {
  authState(): Promise<AuthState>;                       // fresh account/read; throws/times out → treated as 'unavailable' (blocked, see below)
  run(request: CodexTaskRequest, hooks: CodexRunHooks, signal: AbortSignal): Promise<CodexRunResult>;
  cancel(taskId: string): Promise<CancelAck>;           // adapter does turn/interrupt + tool-process cancel; stopped:true only when observed
}
// CodexTaskRequest, CodexRunHooks, CodexRunResult, CancelAck: as ports.ts today, except
//   CodexApprovalRequest gains `category` (ADR-0012 §4) and hooks.toolResult carries ToolResult v2 (§3).
```
Why this shape and not v1's `runTurn(): AsyncIterable` + `interrupt(threadId, turnId)`:
- it is implemented and tested (coordinator 41 tests);
- task-level idempotency (`idempotencyKey`, `attempt`) belongs at this boundary;
- approvals are naturally `Promise`-returning hooks;
- `threadId` is a Codex detail the coordinator keeps only as an opaque handle for resume. The coordinator mints `turnId` (`<taskId>.tN`) and sends it as `clientUserMessageId` (§1, E01 2026-10-19).
- **Thread loading** (E01 2026-10-19, ruling 1s): when a `threadId` is given, the adapter ensures the thread is loaded in this App Server process; if it isn't, it calls `thread/resume` with `excludeTurns:true`, checks that the response echoes the same `threadId`, and fails closed otherwise (`blocked_unavailable`, nothing dispatched). It does this whatever the coordinator's `resume` flag says; the flag only matters when no `threadId` is passed. This makes the D14 tray retry on the prior `threadId` work after a restart. **Condition:** E02 cites the pinned 0.163.0 schema for `thread/resume`, including `excludeTurns`, using the dottie-appserver-contract-diff method; if `excludeTurns` isn't in 0.163.0, it falls back to a plain `thread/resume`. Tests (DOT-090 item 14): an unloaded thread gets resumed; an echo mismatch fails closed.

**Auth gate outcomes (E01 2026-10-19, ADR-0010):** only `signed_in` is admitted. `signed_out` and `expired` → AUTH_REQUIRED and `TaskFinished{outcome:'blocked_auth', reason:'auth_required'}`; `signing_in` → AUTH_REQUIRED with `reason:'sign_in_in_progress'` (copy: finish signing in); `unsupported` → AUTH_REQUIRED with `reason:'account_unsupported'` (copy: this ChatGPT account can't run Codex; offer sign out or switch account, never a reconnect loop). `unavailable` or `unknown`, a throw, or a timeout → `TaskFinished{outcome:'blocked_unavailable', reason:'codex_unavailable'}` (E01 2026-10-19: its own outcome, so the tray can never map it to a sign-in prompt) with **no** AUTH_REQUIRED and no new coordinator state; the supervisor's `RuntimeStatus` (§2.4) carries the environment condition.

**Mid-run and after-commit (E01 2026-10-19):** a Codex auth error during a turn ends `blocked_auth` with reason `auth_required`, or `failed_after_side_effects` with reason `auth_required` if anything was committed. `failed_after_side_effects` accepts any reason from the shared TaskFinished reason set; `validateEvent` rejects reasons outside the set.

**Port deltas (E03 da8215a, E01 2026-10-19):** `CodexError.origin: 'turn_failed' | 'rpc_error' | 'adapter'` is required, and only `turn_failed` may be retried. `CodexRunHooks.codexRetrying()` fires on each `error{willRetry:true}`; the coordinator emits one Reconnecting progress (state RECOVERING) per burst and stays EXECUTING, and nothing is spoken. Retry eligibility uses a **per-turn** ledger read strictly: a possibly side-effecting tool started counts as committed. The task outcome uses the **per-task** ledger, so earlier-turn commits still make a final failure `failed_after_side_effects`. A started tool that then explicitly returns `sideEffect:'none'` does not count toward the outcome (the task ends `failed`). It still blocked the retry. A tool that never returns counts as 'may have taken effect' (E03 d02e545).

**Retry after a possible side effect (E01 2026-10-19, DOT-092; updated (E01 2026-10-19, D14 rulings)):** a user-requested retry after a committed, possible or unknown side effect is a brand-new task with a forced pre-dispatch approval, approvable only in `secure_ui` and never `read` or `navigate` (E01 2026-10-19, ruling 1j); the dialog shows "This action already happened; approving will do it again." (committed) or "This action may already have happened." (possible/unknown) before Approve is enabled. Codex and the model can never set or request it; the coordinator may derive it from its own ledger (DOT-094) (E01 2026-10-19, ruling 1j) (port delta D14, §5; E03 coordinator, E06 approval UI).

**Pre-dispatch confirmation preimage (E01 2026-10-19, E03 886b251):** `method:'dottie.pre_dispatch_confirmation'`, `args:{summary, risk, category, possibleRepeat, retryOfTaskId, displayHash}` (E01 2026-10-19, D14 rulings; E08 co-signed 2026-10-19; ADR-0009 clarification; `displayHash` added (E01 2026-10-19, ruling 1k; E08 co-signed), §3 bound display): `summary`, `risk`, `category` exactly as the dialog shows them (`summary` stays labelled untrusted per X5); `possibleRepeat` = the `priorSideEffect` value (`committed` \| `possible` \| `unknown`) or `null`; `retryOfTaskId` = the prior `taskId` or `null`. Both come only from the coordinator's or K8's own state, never from host, model or Codex input. Changing `possibleRepeat` or `retryOfTaskId` between display and approval invalidates the approval (required tests). A clean-failure retry with a policy-required approval binds `retryOfTaskId` with `possibleRepeat: null`; `requestId` set, `turnId` = the coordinator-minted turnId (so the approval can't be replayed to another turn), and `threadId`, `itemId` and `targets` null. If the approval can't be requested, the task ends `declined` with reason `approval_unavailable`, and the copy never says the user declined. **`displayHash` placement** (E01 2026-10-19, ruling 1q; adds an equality check only, E08 re-sign not needed): CR2's top-level `displayHash` is authoritative for every call: the hash when a dialog is shown, `null` when there's no dialog. Pre-dispatch calls also keep `displayHash` inside `args` (the six-key binding is unchanged), and the two values must be byte-equal; `computeActionId` refuses (fails closed) on a mismatch. Generic gated calls never put `displayHash` in `args`. Required vectors (E02, DOT-090 item 12): pre-dispatch with matching values; pre-dispatch with mismatched values refused; generic with top level only.

`runTurn`/`interrupt`/`ensureThread` become **E02-private** (`AppServerClient`, the wire layer for §1).

### 2.2 `AuthPort`: desktop ↔ Codex adapter (owner E02 implements, E06 consumes; replaces desktop `AuthAdapter.startLogin()` and v1 `beginLogin`)
```ts
interface AuthStatusInfo { status: AuthState; accountLabel: string | null; message: string }   // accountLabel: plan name only unless E08 approves email (DOT-063)
type LoginStarted =
  | { mode: 'browser'; loginId: string }                                        // adapter already opened the URL (ADR-0015); no authUrl here
  | { mode: 'device_code'; loginId: string; verificationUrl: string; userCode: string } // display only; not opened (ADR-0015 item 8)
  | { mode: 'unavailable'; reason: string };
interface AuthPort {
  getStatus(): Promise<AuthStatusInfo>;
  beginLogin(mode: 'browser' | 'device_code'): Promise<LoginStarted>;
  cancelLogin(loginId: string): Promise<'canceled' | 'not_found'>;
  logout(): Promise<void>;                                                         // account/logout, then fresh account/read
  onStatusChange(cb: (s: AuthStatusInfo) => void): () => void;
}
```
- **Auth URL rule (ADR-0015):** `host === 'auth.openai.com'` exactly, `https:`, no userinfo or port, and the URL starts with `https://auth.openai.com/`, plus the §1.2 `account/login/start` parsing checks (open `u.href` only; reject control characters, whitespace, backslashes and non-ASCII hosts; `redirect_uri` = `http://127.0.0.1:<port>/auth/callback` with `<port>` 1455 or Codex's registered fallback). The adapter checks it and only the adapter opens it, after a user click, one login at a time, with a 10-minute timeout.

Kinds `pre_dispatch`, `codex_command` and `codex_file_change` are complete by kind for **every** category, including `read` and `navigate` (so a Codex read command and a D14 read/navigate retry confirmation get a dialog, test C-25 unchanged: fresh approval, no repeat warning for `read`/`navigate`); `ui_action` stays `local_change` or stricter. Exact key names and maximum lengths: E02 in the `ApprovalDisplay` type (DOT-095).
- **Shape: discriminated union** (E01 2026-10-19, ruling 1r; E08 co-signed 2026-10-19): `ApprovalDisplay` has a required `kind: 'tool' | 'ui_action' | 'codex_command' | 'codex_file_change' | 'pre_dispatch'`; `validateEvent` requires each kind's fields and rejects unknown kinds and extra fields; `displayHash` covers `kind`.

- **Binding:** `displayHash` = SHA-256 of the canonical (§3.3 canonicaliser) display object; it is in both the tool-call `actionId` preimage (CR2) and the pre-dispatch preimage (§2.1). Any change to a displayed field changes the `actionId`. `displayHash` is `null` only for gated calls that open no dialog (ratified (E01 2026-10-19, ruling 1l)). **Guard** (E01 2026-10-19, ruling 1l; E08 confirmed 2026-10-19): a call in a dialog category with a `null` `displayHash`, or a no-dialog call with a non-null one → `denied_by_policy{display_unavailable}` (guard test required). ADR-0017 `parentActionId` only references the id value and needs no change; **E02 must regenerate the DOT-090 test vectors** and **E03 must amend the DOT-092 doc preimage** (`docs/contracts/tool-host-control.md`) (E01 2026-10-19, ruling 1l).
- **Approve-enable timer** (E01 2026-10-19, ruling 1l): Approve is enabled only after the dialog has been visible and focused for 500 ms continuously; losing focus (or visibility) resets the timer. The DOT-092 doc (DRAFT 8) defines no such timer, so there is nothing to reconcile there; E03 adds it with the preimage amendment.
- **Rendering:** plain text, no markup or links; in **untrusted free text**, control and bidi-override characters are stripped; in **bound fields** (including path lists and the window title) they are never stripped but rendered as visible highlighted escapes with a "contains hidden characters" badge (DOT-095) (E01 2026-10-19, ruling 1t; E08 co-signed 2026-10-19); fixed maximum lengths with a visible ellipsis (the no-ellipsis exception covers **only** the command field (8 KB) and path lists (500 paths), over which the result is `display_unavailable`; every other field keeps its maximum length plus ellipsis (E01 2026-10-19, ruling 1r; E08 co-signed 2026-10-19)); any model or web free text gets an untrusted-content label.
- **`codex_command` rendering** (E01 2026-10-19, ruling 1t; E08 co-signed 2026-10-19): (1) `\n` is a real line break and the line count is shown; `\r\n` is normalised to `\n` for display only: Codex executes the original bytes, and `displayHash` covers the raw command, not the rendered text. (2) Nothing is stripped: every other control character, a lone `\r`, bidi controls and invisible format characters (zero-width characters, BOM, soft hyphen) render as a visible, highlighted escape such as `<U+202E>` or `\x1b`, a "contains hidden characters" badge appears next to the box, and tab shows as a visible tab marker. (3) Long lines wrap with no horizontal scrolling; trailing whitespace is shown visibly. (4) Escapes count toward the 8 KB limit at their raw byte length; over the limit is still `display_unavailable`, never shortened with an ellipsis. Required tests: a multi-line command shows its lines and line count; a command containing ESC, a lone CR or U+202E renders visibly with the badge, and the executed bytes equal the hashed bytes; wrapping shows no horizontal scroll.
- **Redaction:** the redactor runs on every field before it is displayed or audited; the audit stores `displayHash` only.
- **Fail closed:** if a category's display can't be computed → `denied_by_policy{display_unavailable}`, no generic fallback. The title may stay a category template.

**Rule (E01 2026-10-19):** tool error codes are UPPER_SNAKE (`DENIED_BY_POLICY`); audit `reason` values and all enum values are lowercase snake_case.

**Per-kind ids `actionId` / `taskId` / `toolId` (E01 2026-10-19, DOT-092; approvals item 24 as amended by E01, accepted by E08; narrowed (E01 2026-10-19, DOT-092 ruling 1)):** the three fields are optional in the type. Enforced by **`validateAuditRecord`** in `packages/policy`, the validator for the `dottie.audit` schema (not `validateEvent`, which validates `dottie.event`) (E01 2026-10-19, DOT-092 ruling 2b). Item 24 applies to the K8 tool-host kinds and to tool-host-call records (E01 2026-10-19, DOT-092 ruling 1b):
- `toolhost.peer_rejected`, `toolhost.pipe_squatted`: MUST **omit** all three. A record carrying any of them, even as `null`, is invalid (E08 R4; CR2's "null, never omitted" covers the hash preimage, not audit records).
- `tool_token.minted`, `tool_token.consumed`, `tool_token.rejected`, `tool_token.revoked`, `tool_call.host_refused`: MUST carry all three; a record missing any of them is invalid (tests K-10, K-11).
- `approval.*` and `policy.*` records **about a specific tool-host call** (emitted by the tool host or K8 while gating a `toolId`): MUST carry `taskId`, `actionId` and `toolId`, as doc §5.7 says (E01 2026-10-19, DOT-092 ruling 1b). This includes `policy.denied` for `navigate` and other calls that never ask for approval, with no exemption: the tool host computes an `actionId` for **every** gated tool-host call (§5) (E01 2026-10-19, DOT-092 ruling 1c). **One exception** (E01 2026-10-19, DOT-092 ruling 1e; E08 confirmed): `policy.denied` with `reason:'schema_invalid'` carries `taskId` and `toolId` with `actionId: null`; `validateAuditRecord` allows a null `actionId` only with that reason. That record carries **only** `taskId`, `toolId`, `reason` and timestamps: no args (raw or partial) and no field names from the invalid payload; a redactor canary test is required (E08 confirm).
- `input.field_stripped` (E01 2026-10-19, ruling 1h): `taskId` set when known; MUST **omit** `actionId` and `toolId`.
- Every other kind keeps its existing per-kind rules (unchanged by DOT-092), including Codex-side `approval.*` (§1.4, §2.1 pre-dispatch) and other `policy.*` records (E01 2026-10-19, DOT-092 ruling 1b).

**`source?: 'host'` (E01 2026-10-19, DOT-092 ruling 2):** valid only on `tool_call.host_refused` (where it is required); `validateAuditRecord` (`packages/policy`, `dottie.audit` schema) rejects a record carrying `source` on any other kind (E01 2026-10-19, DOT-092 ruling 2b).

**`input.field_stripped` (E01 2026-10-19, ruling 1h):** `decision:'denied_by_policy'`; fields `field` (`'retryOfTaskId'` | `'possibleRepeat'`), **`sourceChannel`** (required; `voice_worker` | `tray_ipc` | `renderer_ipc` (any renderer-process IPC, E01 2026-10-19, ruling 1w) | `model` | `codex` | `tool_host`, the channel the field arrived on) (E01 2026-10-19, ruling 1i) and `reason:'untrusted_origin'`; `taskId` when known; `actionId` and `toolId` omitted; **`channel` omitted** (it keeps its approval-answer meaning on every other kind) (E01 2026-10-19, ruling 1i). It **never carries the injected value**; `validateAuditRecord` rejects any payload field beyond `decision`, `field`, `sourceChannel`, `reason` and `taskId` (E01 2026-10-19, ruling 1i) and the base record fields (`schema`, `version`, `eventId`, `correlationId`, `causationId`, `timestamp`, `kind`). Redactor canary test required. **Writers:** the main process for `retryOfTaskId` strips (§3 `UtteranceReady`); the coordinator or K8 for `possibleRepeat` values found in model, Codex or tool-host input (§5 D14).

**`decision` on the tool-host kinds (E01 2026-10-19, DOT-092 ruling 3b) (reverses ruling 3; aligned with signed DRAFT 8; existing §3.2 enum values only):** `tool_token.minted` → see the refinement below; `tool_token.consumed` → `approved` for all three outcomes (`consumed`, `consumed_not_dispatched`, `postcondition_unknown`) (E01 2026-10-19, DOT-092, E08 sign-off); `tool_token.rejected` → `denied_by_policy`; `tool_token.revoked` → `revoked` (doc §5.7, D12); `toolhost.peer_rejected` and `toolhost.pipe_squatted` → `denied_by_policy`; `tool_call.host_refused` → `denied_by_policy`.
- **`tool_token.minted` refinement (E01 2026-10-19, DOT-092, E08 sign-off):** outcome `minted` → `approved`. Outcome `refused` → the decision follows the refusal's ToolError: `CANCELLED` → `cancelled`; `DENIED_BY_POLICY` → `denied_by_policy`; `APPROVAL_REQUIRED` → `revoked` when the reason is `revoked` or one of the 12 `tool_token.revoked` revocation reasons (for example `mute`, `locked`, `app_server_restart`) (E01 2026-10-19, DOT-092 ruling 1e; E08 confirmed); `expired` for reason `expired`; `denied_by_policy` for anything else (`wrong_action`, `task_mismatch`, `tool_mismatch`, `reused`). `validateAuditRecord` rejects `tool_token.minted` with `outcome:'refused'` and `decision:'approved'`. Everything else in ruling 3b stands.
- **Required `validateAuditRecord` tests (E01 2026-10-19, DOT-092, E08 sign-off):** (1) a record carrying `source:'host'` on any kind other than `tool_call.host_refused` is rejected; (2) a `tool_token.*` record missing any of `taskId`, `actionId` or `toolId` is rejected.

**Tool-host token and host audit records (E01 2026-10-19, DOT-092; doc §5.7):** written **only by K8 in main**, through the shared redactor (the tool host writes no audit, X1). Fields `{kind, actionId, taskId, toolId, decision, reason?, targetHash?}`, where the three ids are per-kind optional (rule above) and `toolhost.*` omits them (E01 2026-10-19, DOT-092 ruling 1d); never the token string, `tokenId`, `mac`, `nonce` or args.
- **`tool_token.revoked`:** one record per unused token at the moment K8 revokes it. Fields `kind, actionId, taskId, toolId, decision:'revoked', reason, requestedAt` (E01 2026-10-19, DOT-092 ruling 3b) (the token's mint time), `expiresAt`, `resolvedAt` (revocation time). `reason` ∈ `superseded | turn_end | end_task | task_cancel | stop | panic_stop | mute | locked | app_server_restart | ipc_disconnect | main_restart | quit` (12 values, doc §5.5/§5.7; `locked`, not `lock`, per E08 ruling 3). **First cause wins:** the first reason K8 records is never overwritten (a stop followed by `setActiveTurn(null)` stays `stop`). Separate from the approval's own `decision:'revoked'` record, which is still written when the approval itself is revoked. A later use of a revoked token writes `tool_token.rejected{reason:'revoked'}`.
- **`tool_token.consumed`:** one `postcondition_unknown` record when K8 accepts a consume (the approval is then `executed`, §3.3), and a second only on an explicit `toolCallFinished` for that `callId` (`not_started`/`before_send` + `sideEffect:'none'` → `consumed_not_dispatched`; `after_send`/`completed` → `consumed`). No report before IPC disconnect, `endTask` or shutdown → stays `postcondition_unknown` (on disconnect with `reason:'ipc_disconnect'`), ledger `possible`. Never inferred from a late reply; never downgraded after `consumed`.
- **`tool_call.host_refused` (P26):** `source:'host'`; written by K8 from a validated `toolCallFinished.reason` ∈ `known_folder_redirected | locked | schema_invalid | catalog_mismatch | precondition_failed`; any other value (free text, unknown token) is stored as `host_reported_other` with **no text stored**. Informational only: it never changes K8 authority, approval state or the never-downgrade ledger merge; a missing `reason` writes no record and implies nothing.
- **Redactor additions:** sensitive keys `token`, `toolToken`, `approvalToken`, `tokenId`, `mac`, `nonce`; value pattern `\bk8[tr]1\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\b` → `[REDACTED]` (a near-miss such as `k8t1` alone is kept; canary test C-16).

**P25 tool-result mapping (E01 2026-10-19, DOT-092):** an app-server restart is not a user cancel. **Before send** the revoked approval or token never runs and the tool result is `APPROVAL_REQUIRED`, `sideEffect:'none'` (the user may re-approve); `tool_token.revoked` reason `app_server_restart`. **Approved, token minted, revoked by the restart before consume** (E01 2026-10-19, DOT-092 ruling 4b): no pending dialog, so `wireReply:'none'`; audit `tool_token.revoked{reason:'app_server_restart'}`; if the call ever arrives, the gate returns `APPROVAL_REQUIRED` with `sideEffect:'none'`. **Late call after a restart revocation** (E01 2026-10-19, DOT-092, E08 sign-off): K8 writes `tool_token.rejected{reason:'revoked'}` and the ToolError is `APPROVAL_REQUIRED`; it does **not** write `tool_token.revoked` again (that record was written at revocation). **Precedence** (E01 2026-10-19, DOT-092 ruling 1e; E08 confirmed): this P25 rule is the more specific signed rule and overrides the generic doc §4.5 consume mapping for `app_server_restart` only; every other non-cancel revocation (`superseded`, `turn_end`, `end_task`, `mute`, `locked`, `ipc_disconnect`, `main_restart`) keeps `DENIED_BY_POLICY` per doc §4.5 and E04 fix 7. **E01 ruling (accepted by E08, ruling 4):** a restart cancel (`cancelToolCall{reason:'app_server_restart'}`) on a call **already past send** reports `POSTCONDITION_UNKNOWN`, `sideEffect:'unknown'` (§5 three-step rule step 3), never `APPROVAL_REQUIRED` or `sideEffect:'none'`, never downgraded and never re-approved automatically, with no wire reply (`wireReply:'none'`) (E01 2026-10-19, DOT-092 ruling 4). The approval is already `executed`, so it never mints or re-mints (§3.3); audit `tool_token.consumed{outcome:'postcondition_unknown', reason:'app_server_restart'}`; ledger `possible`. **Boundary** = K8's accepted-consume record, whatever the host reports (no accepted consume → the before-send rule; accepted consume → the after-send rule; test C-24b). A user retry follows the D14 rule (§5). `task_cancel`, `panic_stop` and `quit` keep `CANCELLED`.

Silence, "no" and noise produce no approval record of their own; they end as `expired` or `declined`, and tests assert no `approved` record exists.

### 3.3 `RecoveryToken`, `WindowIdentity` and the K8 approval token (E01 2026-10-19; ADR-0017, Proposed; approval token: DOT-092)
```ts
interface WindowIdentity {
  hwnd: string;                           // unsigned decimal string, no leading zeros; "0" is invalid (E08/E04 rule, E01 2026-10-19)
  pid: string;                            // unsigned decimal string, no leading zeros; "0" is invalid (not a number type)
  windowClass: string;                    // plain window class-name string (not a decimal string); 1-256 UTF-16 code units (the Windows count), longer or empty = no identity
  processStartTime: string;               // Windows FILETIME of process creation (GetProcessTimes): 100-ns ticks since 1601-01-01 UTC,
                                          // serialized as an unsigned decimal STRING with no leading zeros (exceeds 2^53), e.g. "133700000000000000";
                                          // never a JSON number, never ISO-8601; "0" is invalid
}
// A zero, empty, signed, zero-padded or non-decimal value in hwnd, pid or processStartTime is invalid: the window has no identity.
// If ANY identity field can't be read, the window has NO identity: it can't be targeted (NOT_FOUND at lookup) and no recovery runs (E01 2026-10-19).
interface RecoveryToken {                 // minted and checked by K8; held in the main process only
  actionId: string;                       // new id for this recovery attempt
  parentActionId: string;                 // actionId of an executed and unexpired desktop.control approval (E01 2026-10-19, DOT-092)
  recoveryAction: 'restore' | 'focus' | 'move_to_monitor';
  taskId: string;
  windowIdentity: WindowIdentity;         // re-resolved at use time, never taken from the model
  nonce: string;                          // 128-bit random, base64url, one per attempt
  mac: string;                            // HMAC-SHA-256(k8Key, canonical MAC input below)
}
```
- `k8Key` is a per-process random key held only by K8; it never leaves the main process and is never logged. The token value (`mac`) is **never logged**.
- Single use: consumed **before** the action runs. Valid only before the parent approval's expiry (never extends it). Revoked by panic-stop, mute, Quit, task cancel, a locked desktop and an app-server restart. Any check failure → deny.
- **MAC input (closed 2026-10-19, E08 rule in `docs/security/recovery-gate-requirements.md`, E08 proposal P-f):** UTF-8 canonical JSON, keys sorted, no whitespace, of
  `{"action":<recoveryAction>,"hwnd":<decimal string>,"nonce":<base64url 128-bit>,"parentActionId":<hex>,"pid":<decimal string>,"processStartTime":<FILETIME decimal string>,"purpose":"dottie.recoveryToken.v1","taskId":<string>,"windowClass":<string>}`.
  `hwnd`, `pid` and `processStartTime` are unsigned decimal strings with no leading zeros; a number, an ISO string or a zero-padded value must fail verification. `windowClass` is the plain class-name string.
- **One canonicaliser (ADR-0009 CR2 + ADR-0017):** keys sorted (ASCII), UTF-8, no whitespace, minimal `JSON.stringify` escaping (Python: `json.dumps(sort_keys=True, separators=(',',':'), ensure_ascii=False)`); every value a string; any non-string value, duplicate key or missing key is rejected, never coerced; one test-vector suite in `packages/policy`. **`displayHash` in CR2** (E01 2026-10-19, ruling 1q; adds an equality check only, E08 re-sign not needed): CR2's top-level `displayHash` is authoritative for every call: the hash when a dialog is shown, `null` when there's no dialog. Pre-dispatch calls also keep `displayHash` inside `args` (the six-key binding is unchanged), and the two values must be byte-equal; `computeActionId` refuses (fails closed) on a mismatch. Generic gated calls never put `displayHash` in `args`. Required vectors (E02, DOT-090 item 12): pre-dispatch with matching values; pre-dispatch with mismatched values refused; generic with top level only.
  - **Scalar leaves (E01 2026-10-19):** every scalar leaf is a string or `null` (null only for fields that don't apply). Numbers and booleans in args are converted to canonical strings before hashing. Nested objects and arrays are allowed: keys sorted recursively, array order preserved.
- **Domain separation (E01 2026-10-19):** the canonical object always carries `purpose`: `"dottie.actionId.v1"` for `actionId` (§3 `ApprovalRequested`) and `"dottie.recoveryToken.v1"` for this MAC. A missing or wrong `purpose` is rejected.
- **K8 approval token (ADR-0009 CR6) (E01 2026-10-19, DOT-092; doc §5.2–§5.8):**
  ```ts
  interface ApprovalToken {               // held by K8 in main-process memory only; never persisted, logged or sent to the renderer
    tokenId: string;                      // 128-bit random, base64url; lookup key only, never logged
    actionId: string; taskId: string; toolId: string;   // binding = taskId + toolId + actionId (turnId stays bound through actionId, CR2)
    nonce: string;                        // 128-bit random, base64url
    expiresAt: string;                    // ISO-8601 with offset
    mac: string;                          // HMAC-SHA-256(k8Key, canonical MAC input), base64url
  }
  ```
  - **MAC input:** this section's canonicaliser over `{"actionId","expiresAt","nonce","purpose":"dottie.approvalToken.v1","taskId","toolId"}`. No `turnId` in the token record or MAC input.
  - **Wire form:** opaque `k8t1.<tokenId>.<mac>` (base64url, no padding), delivered only in `ApprovalResolution.token` or the `requestToolToken` reply over the control channel (§2.5); never in model-visible args or results, MCP `_meta`, `structuredContent` or events. K8 looks up by `tokenId` and verifies `mac` in constant time.
  - **TTL:** `expiresAt = min(approval.expiresAt, mintTime + 10 s)` (the 10 s cap is PROVISIONAL); a token never extends the approval. Single use, burned on any consume attempt (also on mismatch), compare-and-burn atomic; at most one live token per approval (a re-mint revokes the earlier one, reason `superseded`).
  - **Revoked by** `setActiveTurn(null)` (turn end or interrupt), every stop, `endTask`, task cancel, panic-stop, mute, Quit, a locked session, app-server restart, IPC disconnect and main-process restart; one `tool_token.revoked` record each (§3.2).
  - **K8 approval record states:** `pending → approved → executed` (on the first accepted consume), or `expired` / `revoked`. These are **K8 record states, not §3.2 `decision` values**; the §3.2 `approval.*` decisions are unchanged. An approval token is minted only in `approved`; once `executed`, the approval never mints or re-mints an approval token again (E08 R2; this applies to `dottie.approvalToken.v1` only).
  - **Recovery tokens** (this section, ADR-0017) carry the wire prefix **`k8r1.`** and purpose `dottie.recoveryToken.v1`, and are minted **only once K8 has recorded an accepted consume for an unexpired approval** (state `executed`, whether the consume record is `consumed`, `consumed_not_dispatched` or `postcondition_unknown`) (E01 2026-10-19, DOT-092 ruling 5): the approval was spent, so a window restore is legitimate even if dispatch did not complete. Never from a `pending`, approved-but-unconsumed, `expired` or `revoked` approval. Still bound by the WindowIdentity check. `navigate` calls create no approval, so they never parent one.
  - **Cross-rejection:** `consumeToolToken` rejects a recovery token, and the recovery gate rejects an approval token, both **by purpose and by prefix** (`k8t1.` vs `k8r1.`) (test K-05). One `k8Key` (256-bit, per launch, never persisted) serves both, separated by `purpose`.
- **Gate order (E08):** an explicit deny list (`shell_navigate`, `type_text`, `hotkey`, `key_press`, `close_window`, `clipboard_*`, `launch`, `terminate`, `uia_click`, every file mutation) is checked **before** the allowlist and denies with tool error code `DENIED_BY_POLICY` and audit reason `recovery_action_forbidden`; anything else not on the allowlist (`restore`, `focus`, `move_to_monitor`) also gets `DENIED_BY_POLICY`, with audit reason `not_covered`.

## 4. IPC rules
- Every message is schema-validated on receipt and rejected on an unknown `version` or type.
- Renderer ↔ main only through preload-exposed functions.
- No secrets, tokens, auth URLs, raw audio or full file contents cross IPC.
- Correlation IDs are logged. Payloads are logged only after redaction.

## 5. Tool result contract (`dottie-tools`; host per ADR-0008; owners E04/E11)
- MCP `structuredContent` = `{verified, observedState, sideEffect, error?, evidenceRef?}`.
- **`success` is removed** (E11 P2): there is one truth field. MCP `isError` = `!verified`.
- `ObservedState` (redacted object):
  - required keys: `outcome` (verifier enum), `decision` (`done | retry | ask_user | stop`; cancellation is `stop` plus `error.code:'CANCELLED'`, never a `cancelled` value; E01 2026-10-19), `checks: {[checkId]: 'pass'|'fail'|'unknown'}`, `sideEffect`;
  - optional keys: `question` and `candidates` (opaque ids plus safe labels);
  - may also hold tool-specific scalar keys;
  - **never** window titles, file contents or full user paths (use known-folder ids or hashes). Full evidence stays in a local artifact referenced by `evidenceRef`.
- `ToolError = {code, message, retryable}`. `code` is one of `DENIED_BY_POLICY` (policy refused this call: either the action is never grantable, or the required authorization (K8 token, approval) is missing, invalid, expired, used or foreign; ADR-0009 CR6), `PERMISSION_REQUIRED` (scope not granted), `APPROVAL_REQUIRED` (the action is grantable but no approval has been obtained yet), `AMBIGUOUS`, `NOT_FOUND`, `TIMEOUT`,
  `PRECONDITION_FAILED`, `POSTCONDITION_FAILED`, `POSTCONDITION_UNKNOWN`, `CANCELLED`, `INVALID_ARGUMENT` (schema-invalid or malformed arguments, including a malformed `targetId`; `sideEffect:'none'`, not retryable; E01 2026-10-19), `USER_DECLINED` (the user declined an approval; not retried, and the user may re-ask with a new command; E01 2026-10-19), `INTERNAL`.
  `retryable` may be true only when `sideEffect:'none'`. The coordinator ledger rule still applies on top. This is intentional: once a mutating tool has run (`sideEffect` is `committed` or `unknown`), recovery is re-observe first, never a blind retry. Pure observation calls report `sideEffect:'none'` and may be retryable.
- **Success accounting (E01 2026-10-19):** `tool_claimed_success` = the tool's MCP `CallToolResult` has `isError:false`. `false_success` = a claimed success whose verification has `verified:false`. These are the definitions used by the verifier metrics and DOT-064.
- **`observedState.processImage` (optional, E01 2026-10-19):** the process image **basename only** (for example `explorer.exe`), never a full path. It is evidence for the verifier and is **not** part of the window identity (§3.3).
- **Who emits `ToolResult`:** the tool router (coordinator side) wraps the tool's MCP result into the `ToolResult` event, with `causationId` set to the requesting tool-call event. The verifier only returns a `VerificationResult`; it never emits events.
- **Candidate selection (E11 Q4, accepted):** a tool that returned `candidates` accepts an optional `targetId` argument on the follow-up call. It must be an opaque id issued earlier in the same task; an unknown or stale id returns `NOT_FOUND` and is never guessed.
- **Ask-the-user path (E11 P6):** `error.code:'AMBIGUOUS'` plus `observedState.question` (and `candidates`). Codex relays the question and no new event exists. Dottie never guesses a target.
- **Tool-host context and window targeting (E04 review, E01 2026-10-19):**
  - The tool host gets `taskId` and `turnId` for every call from the coordinator over its control channel (the single active task, ADR-0010), never from model-supplied arguments. **Channel (E01 2026-10-19, DOT-092):** specified in `docs/contracts/tool-host-control.md` DRAFT 8 (§2.5). `setActiveTurn{seq, context:{taskId, turnId, threadId|null}}` is advisory (stale `seq` ignored; re-sent after `threadAssigned`); the per-call authority is `authorizeToolCall`, called once per `tools/call` before any lookup or side effect. Checks, first failure wins: a reserved top-level key (`taskId`/`turnId`/`threadId` spellings, `hwnd`, `pid`) → `INVALID_ARGUMENT` (rejected, never stripped); no active turn or a stop requested → `PRECONDITION_FAILED`; `navigate` K8 check (below). Every result here carries `sideEffect:'none'`. Any host cache of an answer is cleared on every `setActiveTurn` and stop. `itemId`/`requestId` come from the MCP request and are informational only. Args are never logged (key names and `argsHash` only).
  - **`targetId` lifetime, host rules (E01 2026-10-19, DOT-092; approvals item 11):** a `targetId` stays valid across all turns of the same task **until `endTask(taskId)`**; after `endTask`, or from another task → `NOT_FOUND`. **Superseded, per window:** when the same window is re-registered under a new id in the same task, only that window's old id → `NOT_FOUND`; other windows' ids and earlier candidate lists stay valid. **30-min cap:** a `targetId` older than 30 min → `NOT_FOUND` even without `endTask` (guards a lost `endTask`; never fires during a normal `AMBIGUOUS` round-trip). The former 300 s TTL is dropped.
  - **`navigate` checks (E01 2026-10-19, DOT-092; approvals items 9, 31):** no approval token. **`actionId` for every gated call (E01 2026-10-19, DOT-092 ruling 1c):** the tool host computes an `actionId` for every gated tool-host call, including `navigate` and other calls that never ask for approval, with `computeActionId` from `packages/contracts` (ADR-0009 CR2; purpose `dottie.actionId.v1`, the same canonicaliser and preimage rules as §3 `ApprovalRequested`). Fail closed: if it can't be computed, the call fails with `DENIED_BY_POLICY`, `sideEffect:'none'`, and Explorer (or any other side effect) is never called (E01 2026-10-19, DOT-092, E08 sign-off); this replaces ruling 1c's `PRECONDITION_FAILED`. "No foreground window" may read as not-foreground only for non-critical checks. An incomplete list stops the action: before the tool runs that's PRECONDITION_FAILED (sideEffect none); after, POSTCONDITION_UNKNOWN (retryable false); a targetId lookup gives NOT_FOUND (reason `enumeration_incomplete`); it is never retried. A `windowClass` containing a lone surrogate (no valid UTF-16 form) means no identity.

    1. **Lookup fails** (unknown, closed, identity mismatch, or no readable identity) → `NOT_FOUND`, `sideEffect:'none'`.
    2. **After lookup, before send** (the window disappears or changes identity) → `PRECONDITION_FAILED`, `sideEffect:'none'`.
    3. **After send** (the window is gone or can't be observed) → `POSTCONDITION_UNKNOWN`, `sideEffect:'unknown'`.
