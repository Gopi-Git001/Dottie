## 3. Codex upstream check (openai/codex @ 8c076942)

- **TypeScript SDK (`sdk/typescript`, package `@openai/codex-sdk`)**: there is **no login API**. `src/codexOptions.ts` exposes only `codexPathOverride, baseUrl, apiKey, config, configOverrides, env`. `src/exec.ts` spawns `codex exec --experimental-json` and maps `apiKey` to `CODEX_API_KEY`. No file in `sdk/typescript/src` references login. So with the TS SDK, ChatGPT sign-in has to come from the CLI's existing login (`codex login`), and the app cannot start or observe it. (This last point is my inference from the code; the README has no auth section.) `exec.ts` does resolve `@openai/codex-win32-x64` / `-win32-arm64` binaries, `codex.exe`.
- **App Server (`codex-rs/app-server`, protocol in `codex-rs/app-server-protocol`)**: **yes, it supports ChatGPT sign-in.**
  - `protocol/common.rs:1301` defines `account/login/start`. Also there: `account/login/cancel`, `account/logout`, `account/read`, plus the notifications `account/login/completed` and `account/updated`.
  - `protocol/v2/account.rs` `LoginAccountParams` has `chatgpt` (browser; the response carries `loginId` and `authUrl`), `chatgptDeviceCode` (`verificationUrl`, `userCode`) and `apiKey`.
  - `chatgptAuthTokens` is marked "[UNSTABLE] FOR OPENAI INTERNAL USE ONLY - DO NOT USE". Do not use it.
  - The Python SDK (`sdk/python/src/openai_codex/_login.py`, `api.py` `login_chatgpt()` / device code) wraps these app-server calls, which confirms this is the official path.
- **Windows native**: **yes, with caveats.**
  - The repo README gives a native PowerShell installer (`irm https://chatgpt.com/codex/install.ps1 | iex`).
  - `codex-rs/windows-sandbox-rs` exists, and the app-server README has a "Windows sandbox implementation selection" section (MXC / elevated / unelevated).
  - developers.openai.com/codex/windows says the CLI and app run "natively in PowerShell with a Windows sandbox instead of requiring WSL". It lists Windows 11 as "Recommended" and MXC as requiring Win11 24H2/25H2 builds ≥ .9278, with legacy `elevated` needing admin setup.
  - Note: `docs/install.md` in the repo still says "Windows 11 **via WSL2**", which looks stale next to the README and the online docs.
- **Implication**: the spec requires an in-app "Sign in with ChatGPT", status, logout and relogin (§5). Only the **App Server** provides that today. The TS SDK would need a CLI-login helper. My recommendation is App Server over stdio from the Electron main process. Pin a released CLI version (the repo's `sdk/typescript/package.json` says `0.0.0-dev`), then run the Week-1 login proof on Windows.

## 4. Top risks

1. **Dollie_Bot_Private is public.** It holds the Dottie Slack bot code and the DM feature. Change it to private if that was the intent. My secret scan of the full history (common key patterns) found only fake test tokens (`sk-fake-test-only`, `xoxb-fake…`) and placeholder docs. **I found no committed secrets in any repo.** MDC `.env.example` keys are placeholders, its tree has no `.env`, and a pattern scan of the four Stage-*.md docs found no keys.
2. **PII in a public repo.** Groot_1.0 commits resumes (`Revanth_Sr.Python AI Engineer.pdf/.docx`, `resume.txt`) and `data/career/*.json`.
3. **Bot's approval logic fails open.** In `voice_assistant.py` (branch), *any* `input_audio_buffer.speech_stopped` after an approval request sets `pending_approval["confirmed"] = True`, so "no" or noise approves. The only gated tools are `terminate_application` and `delete_file`. `close_window`, `type_text`, `hotkey`, clipboard, `move_file` and so on are ungated in code; the prompt alone asks for confirmation. This breaks spec §10, so don't carry it forward. Use MDC's `gate/confirm.py` model instead.
4. **The privacy model conflicts with the spec.** Both voice codebases stream the mic continuously to OpenAI Realtime with an API key. The spec needs local wake and no standby upload, plus separately disclosed STT/TTS billing.
5. **Stack mismatch.** The reusable assets are Python (Bot tools, MDC voice) but the target is Electron/TS. Decide early (ADR) between porting and Python child workers (packaging, signing, supervision).
6. **MDC looks complete but isn't.** It is heavily tested, but every agent and tool is a stub, and it depends on an alpha (`langchain-typesafe`) plus a third-party "Jev" API key. Reuse its logic and tests, not its router.
7. **The best desktop code has no tests.** Bot's desktop/file tools are untested, and their newest work sits on an unmerged branch.
8. **Codex integration.** The app-server protocol is large and fast-moving (many `experimental` fields). The TS SDK lacks login. Both need a version pin and the Week-1 proof.

## 5. Recommendation

**Start a fresh `dottie` monorepo** using the spec §8 layout. Don't extend an existing repo: none of them is Electron/TS-desktop, none has a wake word or Codex, and the closest TS monorepo (Santa_Claus p00) is a different product with Postgres/LangGraph weight and an INCOMPLETE gate. Then:
- **Import with history or attribution, behind adapters:**
  - Bot `tools/desktop_tools.py` + `file_tools.py` (from `fix/unexpected-session-exit`) as a Python tool worker, adding tests before any changes.
  - MDC `voice/echo.py`, `voice/audio.py`, `router/cancel.py` and `gate/confirm.py`, plus their tests.
- **Copy patterns:** Santa_Claus contracts/redaction/check-secrets/CI; Dottie_Bot single-instance lock and dedupe; Groot auth-probe pattern.
- **Leave the old repos untouched (preserve).** Fix visibility on Dollie_Bot_Private and Groot_1.0 if they were meant to be private. Nothing has been changed by this audit.
